implementation recursively inspects arbitrary strings/dictionaries without

The existing false-positive tests check only plain assistant prose, an arbitrary
dict with no explicit wrong `type`, and an unpaired output; they do not exercise
the exact adversarial envelope/item/tool cases. The extraction test's reported
rejection count is largely generated by ordinary unsupported words on normative
lines, while its URL/absolute/traversal tokens occur on a non-normative line and
are not independently asserted through supported evidence forms. It therefore
does not prove the rejection classes claimed in the report.

Additional review gap: `max_evidence_per_candidate` is configured but lacks an
exact boundary test, and evidence-budget exhaustion can create a retained
candidate with zero evidence. Every retained candidate must have at least one
evidence record, even in a manifest explicitly marked incomplete.

## A. Context-aware supported envelope traversal

Replace arbitrary recursive pattern scanning with explicit, documented walkers
for supported API envelope locations. The detector must preserve role/item/tool
context and accept only the shapes it actually proves.

### Project-instruction evidence

- For the captured Responses shape, inspect only the supported top-level/model-
  input message/item location with an allowlisted project-instruction role
  (`developer` for the Codex 0.149.0 captured shape) and `input_text` content
  item. Add a Chat/system/developer variant only if its exact structure is
  documented and tested; do not generalize by scanning every string.
- An identical marker in `assistant`, `tool`, ordinary `user`, metadata, tool
  definitions/arguments/output, arbitrary nested dictionaries, or unrelated
  fields is not project-instruction evidence.
- Continue requiring the full anchored marker plus paired `<INSTRUCTIONS>`
  envelope. Plain/quoted fragments remain false.

### Input-file evidence

- Require an explicit supported input/content item type equal to `input_file`
  in a documented Responses/Chat content position. A dict with `filename` or
  `name` but type `input_text`, `metadata`, tool schema, assistant output, or no
  supported type is not evidence.
- Require exact basename `AGENTS.md` and structurally paired text content in the
  supported item. Unsupported file-ID/base64/remote-only forms no-detect rather
  than guessing content.

### Paired tool-result evidence

- Require a supported tool-call position, exact stable call-ID pairing, and an
  explicit allowlisted read tool/function name. For the captured current shape,
  `exec_command` plus the existing conservative full-command read grammar is
  allowed. Document and test any additional exact name/argument form.
- A function named `delete_all`, `write_file`, unknown/custom tool, a tool
  description, arbitrary dict, mismatched/duplicate/absent call ID, malformed
  arguments, proposed command text, or unpaired output is not evidence even if a
  string contains `cat AGENTS.md`.
- Parsing an embedded arguments string must be bounded/total for the already
  bounded request. Malformed or unsupported nested arguments no-detect with a
  fixed observation status; no raw exception/body and no broad semantic bypass.

Do not detect a root solely because data is syntactically shaped like an API item
inside an unrecognized parent. Supported parent/role/type/pairing is part of the
evidence.

## B. Safe logical `AGENTS.md` path labels

Use one shared deterministic logical-path validator/normalizer for every evidence
class before constructing a root:

- Accept only POSIX repository-relative labels whose basename is exactly
  `AGENTS.md`; normalize safe `./` and repeated separators according to a
  documented rule.
- Current captured absolute effective-directory labels may map to the privacy-
  safe logical label `AGENTS.md` only when the complete captured project envelope
  establishes the root; never persist the absolute host path.
- Reject/no-detect every `..` segment, URL/scheme, POSIX/Windows/UNC absolute or
  network path, NUL/control, percent/query/fragment ambiguity, empty/directory-
  only label, substring/case variant, and path above the configured byte bound.
- Apply the same rule to project directory labels, input filenames, and read-
  command paths. No filesystem/symlink/existence resolution.
- A rejected root path contributes only fixed safe status/reason counts and an
  incomplete/no-detection result as documented; raw path is never logged or
  metric-labeled.

Exact regression cases must include `../AGENTS.md`,
`../outside/AGENTS.md`, `/private/AGENTS.md`, `C:\\private\\AGENTS.md`,
`\\\\server\\share\\AGENTS.md`, `https://example/AGENTS.md`, encoded/query/
fragment variants, `MY_AGENTS.md`, and overlength nested labels for each
applicable evidence class.
